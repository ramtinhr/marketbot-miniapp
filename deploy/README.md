# CI/CD

CI runs on GitHub-hosted Ubuntu runners for pushes and pull requests to `main`.
Existing application tests run before container builds. PRs do not publish images
or receive production secrets. Successful main builds publish `sha-<full commit
SHA>` and `latest` to GHCR. External workflow actions are pinned to commits.
Container verification checks the web health endpoint for static web images and
module parsing in the API/engine/server images; full dependency readiness is
checked during deployment.

Run **Actions → Deploy → Run workflow** on `main` after its CI succeeds:

- `delivery=source` (default) archives exactly that workflow's commit, uploads it
  through SSH, and builds on the server using its persistent Docker cache.
  Runtime secrets stay outside the build context. Existing services keep running
  during transfer and build. Source mode rebuilds rather than reusing the CI image.
- `delivery=image` pulls the CI image on the runner and transfers it over SSH.
  Leave `image_tag` blank for `sha-<workflow commit SHA>`, or select an earlier
  successful `sha-<full commit SHA>` to roll back. `latest` is also supported.
  The server needs no GHCR credentials. Install rsync on runner and host for
  incremental layer transfer; otherwise the script uses gzip/scp.

The production host needs Bash, Docker with BuildKit, Compose v2 supporting
`up --wait --wait-timeout`, tar/gzip, and enough disk space. Source mode also
needs access to base-image registries and npm and enough build memory/CPU.
Image mode supports hosts without registry access. The deploy timeout is six
hours; workflows serialize deployments to each project.

## GitHub production environment

Create a `production` environment restricted to `main`, and configure:

| Setting | Kind | Value |
| --- | --- | --- |
| `SSH_HOST` | Secret | Hostname or IPv4 address |
| `SSH_USER` | Secret | User able to run Docker and write the deployment directory |
| `SSH_PRIVATE_KEY` | Secret | Dedicated deployment private key |
| `SSH_KNOWN_HOSTS` | Secret | Server host key verified through a trusted channel |
| `MINIAPP_ENV` | Secret | Entire runtime dotenv file; start from [runtime.env.example](runtime.env.example) |
| `MINIAPP_DEPLOY_PATH` | Variable, required | `/opt/marketbot-miniapp`, or another absolute dedicated directory |
| `SSH_PORT` | Variable, optional | Defaults to `22` |
| `TELEGRAM_BOT_TOKEN` | Secret, optional | CI/deploy notification bot |
| `TELEGRAM_CHAT_ID_CICD` | Secret, optional | Notification chat ID |

`GITHUB_TOKEN` is supplied by Actions. Grant package read access if needed.
Image references are generated by deployment; omit them from the runtime secret.
No `LOCAL_REGISTRY` or registry credentials on the server are needed by this flow.
Optional Telegram notifications are configured in CI and deployment workflows.

## Releases and readiness

Each deployment creates `releases/<run-id>-<attempt>` with a private dotenv file,
release-specific image tags, and its Compose configuration. A healthy deployment
updates `current`. Failed startup prints logs, container state and health-check
output before restoring the previous release. A failed first deployment with
nothing to restore stops the failed stack. Application rollback still returns a
failed workflow result so the failed deployment is visible.

Existing flat installations are snapshotted into a legacy release before their
first replacement. Existing images are pinned locally for rollback, and the
Compose project name is retained. Do not delete old release images or directories
if automatic rollback is needed. Use `cd <deploy-path>/current` for subsequent
manual Compose commands. Deployment may briefly interrupt traffic during restart.
Database changes and external effects are not undone by application rollback.

## Shared host ports

| Project | Runtime setting | Typical port |
| --- | --- | --- |
| API | `PORT` | `8080` |
| Dashboard | `WEB_PORT` | `8081` |
| Miniapp web | `WEB_PORT` | `8082` |
| Miniapp server | `SERVER_PORT` | `8090` |
| Customer frontend | `FRONTEND_PORT` | `3002` |
| Engine | No HTTP listener | — |

These are separate loopback listeners using host networking. Confirm a port is
free before selecting it (`sudo ss -ltnp 'sport = :3002'`). Stop an obsolete
instance through its service manager, or use another free port and update the
reverse proxy. Keep API `WEB_PORT` equal to dashboard `WEB_PORT`, and API
`MINIAPP_PORT` equal to miniapp `WEB_PORT`. The frontend public origin and proxy
upstream must also match its selected domain and port.

## Miniapp specifics

Source mode builds both `server/Dockerfile` and `web/Dockerfile` from the root.
Image mode transfers both `/server` and `/web` GHCR images. Set the public GitHub
variable `BOT_USERNAME` for the web build; the same value may also be needed in
`MINIAPP_ENV` for server-generated links. This is a build setting, not a secret.
Readiness checks the server's `/health/ready`, both container health checks, and
the web proxy's `/api/v1/market/symbols`. Deploy the bot, engine, API and their
required schemas first. All server options are documented in
[server/.env.example](../server/.env.example). The existing Compose runtime mode
is preserved by this CI/CD change; configure service behavior separately.
